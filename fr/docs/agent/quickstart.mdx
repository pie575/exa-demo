Exa Agent est un endpoint asynchrone facturé à l&#39;utilisation, conçu pour les tâches gourmandes en calcul comme la constitution de listes, l&#39;enrichment et la deep research. Il gère les raisonnements complexes et peut renvoyer de nombreux fields d&#39;output structuré.

Voyez-le comme un agent de context : vous décrivez les données que vous voulez et la forme sous laquelle elles doivent vous parvenir, et Exa Agent orchestre les appels d&#39;outil nécessaires pour y arriver. Un seul run peut lancer de nombreuses recherches sous différents angles, lire et condenser les pages correspondantes, découper la constitution de listes en sous-tâches exécutées en parallèle, vérifier chaque candidat au regard de vos critères, enrichir les contacts et interroger les data partners [Exa Connect](/fr/docs/agent/connect/overview) que vous y attachez. Vous récupérez le context assemblé sous la forme d&#39;un résultat unique, structuré et fondé sur des preuves, plutôt que d&#39;orchestrer vous-même chaque appel `/search` et `/contents`.

Chaque run peut renvoyer une réponse en langage naturel, du JSON validé par schéma, un grounding au niveau des fields, des métadonnées et un détail des coûts. Vous pouvez récupérer ultérieurement les runs terminés, lister les runs passés, rejouer les events ou reprendre à partir d&#39;un run précédent.

<Tip>
  Vous préférez MCP ? Exa Agent et [Exa Connect](/fr/docs/agent/connect/overview) sont disponibles dans [Exa MCP](/fr/docs/get-started/exa-mcp#exa-agent). Activez `tools=agent_run` pour exécuter des recherches multi-étapes, de la constitution de listes, de l&#39;enrichment et de l&#39;output structuré depuis Claude, Cursor et d&#39;autres clients MCP.
</Tip>

## Quand utiliser Exa Agent {#when-to-use-exa-agent}

Utilisez Exa Agent lorsqu&#39;un workflow nécessite plus qu&#39;un simple appel de recherche ou d&#39;extraction, ou lorsque vous devriez sinon écrire votre propre loop de recherches, de lectures de pages et d&#39;étapes de vérification pour rassembler les données :

* Construire des listes à partir de critères ouverts, puis enrichir chaque résultat
* Rechercher des entités sur de nombreux fields, avec citations
* Exécuter des tâches multi-étapes comme « trouver des entreprises, puis leurs décideurs »
* Produire du JSON structuré à partir d&#39;une tâche de recherche web de longue durée
* Combiner recherche web et data partners premium dans une seule réponse fondée sur des preuves
* Poursuivre un run précédent avec une requête de suivi du type « trouve 10 résultats de plus »

Exa Agent présente par conception une latence plus élevée et un fonctionnement asynchrone. Pour une simple recherche à faible latence où vous orchestrez les appels vous-même, commencez par la [Search API](/fr/docs/search/quickstart).

## Quickstart {#quickstart}

Cet exemple lance un run qui construit une liste structurée de personnes correspondant à vos critères. Il renvoie du JSON dans `output.structured`.

<CodeGroup>
  ```python Python theme={null}
  import json
  from exa_py import Exa

  exa = Exa()
  run = exa.agent.runs.create(
      query="Find engineering leaders at AI infrastructure companies that raised a Series A or B in the last 6 months.",
      output_schema={
          "type": "object",
          "properties": {
              "people": {
                  "type": "array",
                  "maxItems": 10,
                  "items": {
                      "type": "object",
                      "properties": {
                          "name": {"type": "string"},
                          "job_title": {"type": "string"},

                      },
                      "required": ["name", "job_title", "linkedin_url"],
                  },
              }
          },
          "required": ["people"],
      },
      effort="auto",
  )

  print(json.dumps(run.model_dump(), indent=2))
  ```

### 4. Interroger le run jusqu&#39;à son achèvement {#4-poll-for-completion}

Si vous n&#39;utilisez pas le streaming d&#39;events, conservez l&#39;`id` retourné et interrogez le run jusqu&#39;à ce qu&#39;il atteigne un statut terminal.

<CodeGroup>
  ```python Python theme={null}
  import json
  from exa_py import Exa

  exa = Exa()
  run_id = "agent_run_01j..."
  run = exa.agent.runs.poll_until_finished(
      run_id,
      poll_interval=4000,
  )

  print(json.dumps(run.model_dump(), indent=2))
  ```

  ```javascript JavaScript theme={null}
  import Exa from "exa-js";

  const exa = new Exa();
  const runId = "agent_run_01j...";
  const run = await exa.agent.runs.pollUntilFinished(runId, {
    pollInterval: 4000
  });

  console.log(JSON.stringify(run, null, 2));
  ```

  ```bash cURL theme={null}
  RUN_ID="agent_run_01j..."

  while true; do
    RUN_JSON="$(curl -s "https://api.exa.ai/agent/runs/$RUN_ID" \
      -H "Authorization: Bearer $EXA_API_KEY")"

    STATUS="$(echo "$RUN_JSON" | python3 -c 'import json,sys; print(json.load(sys.stdin)["status"])')"
    echo "status=$STATUS"

    if [ "$STATUS" = "completed" ] || [ "$STATUS" = "failed" ] || [ "$STATUS" = "cancelled" ]; then
      echo "$RUN_JSON"
      break
    fi

    sleep 4
  done
  ```
</CodeGroup>

Les runs terminés contiennent :

* `output.text` : une réponse en langage naturel
* `output.structured` : du JSON validé lorsque vous fournissez `outputSchema`
* `output.grounding` : les citations du texte ou des fields structurés, lorsqu&#39;elles sont émises
* `costDollars` : le détail du cost du run

<Note>
  Exa Agent est également disponible via l&#39;API Responses compatible OpenAI. Pointez
  le SDK OpenAI vers `https://api.exa.ai`, utilisez `model: "exa-agent"`, puis choisissez
  une exécution synchrone, en streaming ou en arrière-plan. Voir [Compatibilité avec le SDK
  OpenAI](/fr/docs/integrations/openai-sdk#agent-via-responses-api).
</Note>

## Stream events {#stream-events}

Le streaming maintient la requête de création ouverte et envoie des Server-Sent Events (SSE) jusqu&#39;à la fin du run. Consultez [Event format](#event-format) pour connaître les event types et les payloads.

Définissez `stream=True` en Python, `stream: true` en JavaScript, ou envoyez `Accept: text/event-stream` en HTTP :

<CodeGroup>
  ```python Python theme={null}
  from exa_py import Exa

  exa = Exa()
  events = exa.agent.runs.create(
      query="Find five recently launched developer tools for evaluating AI agents.",
      stream=True,
  )

  for event in events:
      print(event.event, event.data)
  ```

  ```javascript JavaScript theme={null}
  import Exa from "exa-js";

  const exa = new Exa();
  const events = await exa.agent.runs.create({
    query: "Find five recently launched developer tools for evaluating AI agents.",
    stream: true
  });

  for await (const event of events) {
    console.log(event.event, event.data);
  }
  ```

  ```bash cURL theme={null}
  curl -N -X POST "https://api.exa.ai/agent/runs" \
    -H "Content-Type: application/json" \
    -H "Accept: text/event-stream" \
    -H "Authorization: Bearer $EXA_API_KEY" \
    -d '{
      "query": "Find five recently launched developer tools for evaluating AI agents."
    }'
  ```
</CodeGroup>

### Format des events {#event-format}

Chaque trame SSE contient un identifiant d&#39;event, un nom d&#39;event et un payload JSON :

```text theme={null}
id: 1
event: agent_run.created
data: {"id":"agent_run_01j...","status":"queued","createdAt":"2026-05-07T21:21:52.051Z"}
```

Le stream peut également contenir des lignes de commentaire telles que `: keep-alive`. Les clients SSE ignorent automatiquement les commentaires ; les parseurs personnalisés doivent faire de même.

### Types d&#39;events {#event-types}

| Event                 | payload `data`                        | Utilisation                                                                                                                 |
| --------------------- | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `agent_run.created`   | `{ id, status: "queued", createdAt }` | Enregistrez l&#39;ID du run dès que la requête est acceptée.                                                                |
| `agent_run.started`   | `{ id, status: "running" }`           | Marquez le run comme étant en cours de traitement.                                                                          |
| `agent_run.completed` | L&#39;objet Agent run terminé         | Lisez la réponse finale dans `data.output.text` ou `data.output.structured`, et les citations dans `data.output.grounding`. |
| `agent_run.failed`    | `{ id, status: "failed", error }`     | Affichez `error.code` et `error.message` ; aucun output final n&#39;est disponible.                                         |
| `agent_run.cancelled` | `{ id, status: "cancelled", ... }`    | Cessez de consommer le stream et traitez le run comme annulé.                                                               |

Les events associés à une même étape de recherche comportent un `callId`, qui correspond à `item.call_id` dans les events de progression des outils. Utilisez-le pour regrouper les traces de search, les sources et la progression des outils. Certaines descriptions de traces de search sont générées de manière asynchrone et peuvent arriver après la source ou l&#39;event d&#39;outil qu&#39;elles décrivent : ne les corrélez donc pas uniquement selon leur ordre d&#39;arrivée.

Considérez `agent_run.source.added` comme un aperçu en direct, et non comme une liste de citations complète. Le champ `output.grounding` du run terminal constitue l&#39;output de grounding faisant autorité.

### Rejouer les events stockés {#replay-stored-events}

Pour les runs non-ZDR, [`GET /agent/runs/{id}/events`](/fr/docs/reference/agent-api/list-run-events) renvoie les events stockés sous forme de JSON paginé. Envoyez `Accept: text/event-stream` pour rejouer les events stockés en SSE, et `Last-Event-ID` pour ignorer ceux que votre client a déjà traités :

```bash cURL theme={null}
curl -N "https://api.exa.ai/agent/runs/agent_run_01j.../events" \
  -H "Accept: text/event-stream" \
  -H "Last-Event-ID: 12" \
  -H "Authorization: Bearer $EXA_API_KEY"
```

L&#39;endpoint de replay envoie les events stockés au moment de la requête, puis se ferme ; il ne continue pas à suivre un run en cours. Les runs ZDR ne conservent pas les events et ne peuvent donc pas être rejoués.

Pour assurer la compatibilité ascendante, ignorez les noms d&#39;events que votre application ne reconnaît pas et poursuivez jusqu&#39;à réception d&#39;un event terminal.

## Renvoyer du JSON structuré {#return-structured-json}

Utilisez `outputSchema` pour renvoyer du JSON validé par un schéma dans `output.structured`.

`outputSchema` prend en charge la [spécification JSON Schema](https://json-schema.org/).

Pour demander des informations de contact, décrivez les fields de contact souhaités dans `outputSchema`. Utilisez les structures JSON Schema standard, par exemple `{ "type": "string", "format": "email" }` pour les adresses e-mail, `{ "type": "string", "format": "phone" }` pour les numéros de téléphone et `{ "type": "string", "format": "uri" }` pour les URL. Limitez autant que possible la taille des listes avec `maxItems` afin de rendre prévisible le coût maximal de l&#39;enrichment de contacts.

## Traiter les lignes d&#39;entrée {#process-input-rows}

Utilisez `input.data` lorsque vous disposez déjà d&#39;un ensemble de données que vous souhaitez enrichir. Vous pouvez ajouter des field supplémentaires à chaque entité de données, faire ressortir de nouvelles entités à partir des données fournies, ou les deux.

Pour des exemples complets d&#39;enrichment de lignes, consultez les [exemples d&#39;Agent](/fr/docs/agent/examples#enrich-input-rows-code).

## Traiter les exclusions {#process-exclusions}

Utilisez `input.exclusion` pour empêcher certaines entrées d&#39;apparaître dans le run. Dans l&#39;exemple ci-dessous, nous recherchons les 10 animaux les plus mignons, mais nous excluons les chèvres et les pandas du run, car nous savons déjà à quel point ils sont mignons.

<CodeGroup>
  ```python Python theme={null}
  import json
  ```

## Connecter des sources de données {#connect-data-sources}

L&#39;index est déjà disponible à chaque run. Utilisez `dataSources` uniquement pour attacher des partners [Exa Connect](/fr/docs/agent/connect/overview). Chaque entrée sélectionne un `provider`. Lorsqu&#39;une propriété de votre `outputSchema` fait référence à une source spécifique (par exemple, &quot;from Similarweb&quot;), Exa Agent appelle l&#39;outil du fournisseur correspondant plutôt que de deviner à partir d&#39;une page web.

```json theme={null}
{
  "dataSources": [
    { "provider": "similarweb" },
    { "provider": "fiber" }
  ]
}
```

Consultez [Exa Connect](/fr/docs/agent/connect/overview) pour la liste complète des data partners, avec des exemples pour chacun.

## Tarification {#pricing}

Les coûts dépendent de l&#39;utilisation et sont facturés par composant :

| Composant                 | Prix              |
| ------------------------- | ----------------- |
| Agent Compute Units       | `1 ACU = $0.10`   |
| Appels d&#39;outil Search | `$0.005 / search` |

<Note>
  L&#39;enrichissement de contact est distinct des composants de tarification principaux ci-dessus : l&#39;enrichissement de contact par e-mail coûte `$0.02 / email` et l&#39;enrichissement de contact par numéro de téléphone coûte `$0.07 / phone number`.
</Note>

`usage.agentComputeUnits` mesure le calcul du modèle sur l&#39;ensemble du run. Les requêtes complexes, en particulier celles comportant un field `input.data` volumineux, nécessitent davantage d&#39;étapes de raisonnement et d&#39;appels d&#39;outil, et consomment donc plus d&#39;ACU.

Consultez [Limites de l&#39;Agent](/fr/docs/admin/billing#agent-limits) pour connaître la concurrency et les limites de débit.

### Effort {#effort}

Utilisez `effort` pour choisir un niveau de coût et de raisonnement pour chaque run. Les valeurs prises en charge sont `minimal`, `low`, `medium`, `high`, `xhigh`, `auto` et `max` ; la valeur par défaut est `auto`. Les efforts fixes ont un prix prévisible par requête, tandis que `auto` et `max` (bêta) sont facturés à l&#39;utilisation :

| Effort    | Prix                                                                              |
| --------- | --------------------------------------------------------------------------------- |
| `minimal` | `0,012 $ / request`                                                               |
| `low`     | `0,025 $ / request`                                                               |
| `medium`  | `0,10 $ / request`                                                                |
| `high`    | `0,50 $ / request`                                                                |
| `xhigh`   | `1,00 $ / request`                                                                |
| `auto`    | Facturé à l&#39;utilisation ; jusqu&#39;au plafond par défaut de `5 $`            |
| `max`     | **Bêta**, facturé à l&#39;utilisation ; jusqu&#39;au plafond par défaut de `20 $` |

<Info>
  Agent Max est le niveau d&#39;effort le plus élevé, destiné aux travaux où l&#39;exhaustivité
  et la rigueur priment sur la latence ou le coût, notamment la constitution de
  listes volumineuses, la recherche approfondie multi-sources et les critères difficiles
  à vérifier. Il est en bêta publique : les requêtes avec `effort: "max"` doivent inclure
  `Exa-Beta: agent-max-effort-2026-07-27`. Le header accepte une liste de jetons bêta
  séparés par des virgules.
</Info>

`budget.maxCostDollars` est un plafond facultatif par run pour `auto` et `max`. Il accepte des valeurs de `1 $` à `100 $` ; le maximum livré est de `100 $`, mais le serveur peut configurer un maximum inférieur. Le plafond par défaut est de `5 $` pour `auto` et de `20 $` pour `max`. Il s&#39;agit d&#39;un plafond et non d&#39;un prix fixe : les runs qui se terminent plus tôt coûtent moins cher. Le budget n&#39;est pas accepté pour les efforts fixes.

### Choisir un mode d&#39;effort {#choosing-an-effort-mode}

Les modes d&#39;effort fixes conviennent bien lorsque vous souhaitez une tarification prévisible par requête pour de la recherche standard. Utilisez `auto` pour les travaux à portée variable comme la constitution de listes, où le nombre d&#39;entités peut varier d&#39;une requête à l&#39;autre.

| Effort    | Idéal pour                                                                       | Complexité de schéma suggérée                                                     | Durée d&#39;exécution attendue       |
| --------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------ |
| `minimal` | Recherches au coût le plus bas, tâches factuelles très ciblées, réponses courtes | Un ou deux field, schéma peu profond                                              | Le moins cher, le moins exhaustif    |
| `low`     | Recherches simples, tâches factuelles ciblées, réponses courtes                  | Quelques field, schéma peu profond                                                | Rapide, recherche légère             |
| `medium`  | Point de départ par défaut pour la plupart des tâches de recherche standard      | Nombre modéré de field, objets imbriqués simples                                  | Équilibre qualité/durée              |
| `high`    | Recherche plus difficile, davantage de citations, exigence de complétude accrue  | Schémas plus vastes ou field plus nuancés                                         | Plus lent, plus approfondi           |
| `xhigh`   | Tâches à forte valeur où la complétude prime sur le coût et la latence           | Schémas complexes, nombreux field, vérification difficile                         | Le plus lent des efforts fixes       |
| `auto`    | Travaux à portée variable, constitution de listes, difficulté de tâche inconnue  | Flexible ; utile lorsque le nombre d&#39;entités ou le travail requis est inconnu | Variable                             |
| `max`     | Recherche à l&#39;effort le plus élevé (bêta)                                    | Schémas complexes, nombreux field, vérification difficile                         | Durée d&#39;exécution la plus longue |

Commencez par `medium` pour de la recherche standard sur une seule entité. Descendez à `low` ou `minimal` lorsque le coût et la latence comptent plus que la complétude. Passez à `high` ou `xhigh` lorsque le schéma de sortie est plus vaste, que les field nécessitent une vérification ou que la tâche exige un raisonnement plus poussé. Utilisez `auto` lorsque vous ne connaissez pas la portée à l&#39;avance, par exemple pour la constitution de listes ou des workflows susceptibles de renvoyer de nombreuses entités.

La durée d&#39;exécution varie selon la difficulté de la requête, la complexité du schéma et la disponibilité des sources externes. Considérez les modes d&#39;effort comme des compromis qualité/coût/durée plutôt que comme des garanties strictes de latence.

## Zero Data Retention {#zero-data-retention}

Exa Agent prend en charge le [Zero Data Retention](/fr/docs/admin/security/zero-data-retention) (ZDR). Le ZDR s&#39;active par team. [Contactez-nous](mailto:sales@exa.ai) pour l&#39;activer sur votre compte.

Lorsque le ZDR est activé pour votre team :

* Créez des runs en streaming (`Accept: text/event-stream`) pour consommer l&#39;output en direct, ou interrogez les runs asynchrones par polling pendant la fenêtre de rétention.
* Les données d&#39;un run sont disponibles pendant son exécution et jusqu&#39;à 10 minutes après qu&#39;il a atteint un état terminal. Passé ce délai, le run ne peut plus être récupéré.
* `previousRunId` n&#39;est pas disponible.
* Les `dataSources` d&#39;Exa Connect ne sont pas disponibles ; les requêtes qui en contiennent renvoient une erreur `400`.
